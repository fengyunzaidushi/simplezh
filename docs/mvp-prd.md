# SimpleZH MVP 产品规格

> 文档状态：Draft
>
> 版本：0.1
>
> 日期：2026-09-27

## 1. 产品定位

SimpleZH 是一个面向中文内容生产者的简繁转换 SaaS。它帮助用户把文章转换为简体、通用繁体、台湾正体或香港繁体，并尽量保留原始格式，转换结果可以直接复制或下载发布。

MVP 的核心承诺是：**转换结果稳定、格式不乱、常用地区词汇更符合目标读者习惯。**

第一版是文章转换工作台，不是通用翻译平台，也不承担内容改写、润色或事实校对。

## 2. 目标用户

### 2.1 首要用户

- 自媒体、公众号、博客作者
- 小说、漫画、游戏文本运营者
- 需要制作两岸三地内容版本的企业内容人员

### 2.2 典型任务

1. 用户已有一篇简体中文文章，需要发布台湾正体版本。
2. 用户从繁体来源整理内容，需要转换成简体中文再编辑。
3. 用户需要将同一篇文章转换成多个地区版本。
4. 用户有固定品牌词汇，希望转换时始终使用自己的术语。

## 3. MVP 目标与非目标

### 3.1 目标

- 用户在 1 分钟内完成第一次转换。
- 支持纯文本、Markdown 和基础 HTML 内容。
- 支持简体、通用繁体、台湾正体、香港繁体之间的主要转换路径。
- 转换后保留 Markdown 和基础 HTML 结构。
- 用户可以使用自定义词汇表修正默认转换结果。
- 游客可以试用，注册用户可以保存记录和词汇表。
- 能统计转换次数、字符数、失败原因和结果操作。

### 3.2 非目标

- 不做大模型翻译、改写或润色。
- 不做 PDF、Word、Excel 的复杂排版转换。
- 不做浏览器插件和第三方平台自动发布。
- 不做团队协作、审批流和企业权限体系。
- 不做开放 API、批量任务队列和支付订阅的完整闭环。

## 4. 产品范围

### 4.1 MVP 必须包含

| 模块 | 功能 | 优先级 |
| --- | --- | --- |
| 转换工作台 | 输入、转换、结果预览、交换输入输出 | P0 |
| 转换设置 | 方向、目标地区、标点和全角字符设置 | P0 |
| 结果操作 | 复制、下载 TXT、下载 Markdown、导出 HTML | P0 |
| 格式保护 | Markdown 结构、HTML 标签、代码块、URL 保护 | P0 |
| 词汇表 | 手动添加、编辑、删除、启用词条 | P0 |
| 账户 | 注册、登录、退出 | P1 |
| 历史记录 | 查看最近转换任务并重新打开 | P1 |
| 用量限制 | 游客和注册用户的字符数限制 | P1 |
| 基础统计 | 转换字符数、耗时、成功和失败状态 | P1 |

### 4.2 后续版本

- CSV 词汇表导入和导出
- 批量文件转换
- API 和 Webhook
- 团队词汇表
- 订阅和支付
- Word、PDF 等文档格式
- 浏览器扩展

## 5. 核心用户流程

### 5.1 游客首次转换

```text
进入首页
  -> 粘贴或输入内容
  -> 选择转换方向和目标地区
  -> 点击“开始转换”
  -> 查看结果和差异统计
  -> 复制或下载
```

游客不需要登录即可完成小文本转换。达到游客额度后，页面提示注册并保留当前输入内容。

### 5.2 注册用户使用词汇表

```text
进入词汇表
  -> 创建或选择词汇表
  -> 添加源词和目标词
  -> 在转换工作台启用词汇表
  -> 执行转换
  -> 复制、下载或保存记录
```

### 5.3 历史记录重用

```text
进入历史记录
  -> 查看任务状态、方向、字符数和时间
  -> 重新打开任务
  -> 修改设置或词汇表
  -> 再次转换并生成新结果
```

## 6. 功能规格

### 6.1 转换工作台

#### 输入区

- 默认显示空状态和示例占位内容。
- 支持粘贴文本。
- 支持拖拽或选择 `.txt`、`.md`、`.html` 文件，文件大小上限由额度规则控制。
- 显示当前字符数和预计消耗额度。
- 输入内容发生变化时，允许清空，但必须二次确认。

#### 设置区

- 源语言：自动识别、简体、通用繁体、台湾正体、香港繁体。
- 目标语言：简体、通用繁体、台湾正体、香港繁体。
- 转换方向和源目标相同时，禁止提交并提示无需转换。
- 是否转换标点：默认开启。
- 是否转换全角字符：默认关闭。
- 当前启用词汇表：默认不启用，注册用户可选择个人词汇表。

#### 结果区

- 显示转换后的文本。
- 显示转换状态：等待、处理中、成功、失败。
- 显示转换前后字符数和处理耗时。
- 提供复制、下载和再次转换操作。
- 复制失败时提供备用的手动选择提示，不丢失结果内容。

### 6.2 格式保护

MVP 需要保护以下内容，不应被转换器当作普通正文改写：

- Markdown 标题、列表、引用、表格、代码块和行内代码
- Markdown 链接 URL、图片 URL 和 HTML 标签
- HTML 标签名、属性名、属性值中的 URL
- 代码块内容
- 邮箱地址、普通 URL 和文件路径

纯文本模式不做结构保护，只按文本转换。

### 6.3 自定义词汇表

词条字段：

- `source_term`：源词
- `target_term`：目标词
- `note`：可选备注
- `enabled`：是否启用

规则：

- 同一词汇表内源词必须唯一。
- 空词条不允许保存。
- 词条匹配应优先处理更长的源词，避免短词覆盖长词。
- 自定义词条覆盖默认转换结果。
- 转换结果中展示应用的词条数量。

示例：

| 源词 | 目标词 | 备注 |
| --- | --- | --- |
| 视频 | 影片 | 台湾用语 |
| 软件 | 軟體 | 产品内容 |
| 账号 | 帳號 | 产品内容 |
| 服务器 | 伺服器 | 技术内容 |

### 6.4 历史记录

历史记录保存最近任务的元数据，至少包括：

- 任务 ID
- 用户 ID
- 输入类型
- 源语言和目标语言
- 使用的词汇表
- 输入和输出字符数
- 任务状态
- 创建时间和完成时间

MVP 默认保存结果内容，用户可以手动删除。后续需要根据隐私策略增加“只保存元数据”的选项。

## 7. 转换规则与质量边界

### 7.1 转换引擎

使用 OpenCC 或兼容实现作为确定性转换引擎，不使用大模型作为默认转换路径。

原因：

- 结果可重复。
- 处理成本稳定。
- 延迟和失败面更可控。
- 适合批量转换。

### 7.2 地区版本

MVP 采用以下内部标识：

| 显示名称 | 内部标识 |
| --- | --- |
| 简体中文 | `zh-CN` |
| 通用繁体 | `zh-TW` 或 OpenCC 对应通用繁体配置 |
| 台湾正体 | `zh-TW` |
| 香港繁体 | `zh-HK` |

实际配置名称以所选 OpenCC 实现支持的配置为准，产品层不直接暴露库文件名。

### 7.3 已知边界

- 专有名词、品牌名、人名和新词可能需要词汇表修正。
- 转换不是翻译，不保证目标地区的完整本地化表达。
- 图片内文字不会被处理。
- 复杂富文本和复杂 Office 排版不属于 MVP 保证范围。

## 8. 技术方案

### 8.1 推荐技术栈

- 前端：Next.js、TypeScript、Tailwind CSS
- 服务端：Next.js Route Handler 或 Node.js API
- 转换：OpenCC 的 Node.js 或 WASM 实现
- 数据库：PostgreSQL
- 认证：Supabase Auth 或同类托管认证服务
- 部署：支持 Node.js 的托管平台

### 8.2 处理链路

```text
客户端提交文本
  -> 校验用户身份和额度
  -> 校验输入格式和大小
  -> 解析并保护 Markdown / HTML 结构
  -> 执行 OpenCC 基础转换
  -> 应用自定义词汇表
  -> 恢复受保护片段
  -> 校验结构完整性
  -> 返回结果并记录用量
```

### 8.3 可靠性要求

- 转换前保留原始输入，转换失败时可以重试。
- 服务端设置单任务超时。
- 单次任务必须有明确的成功或失败状态。
- 失败不消耗完整额度，具体扣费规则在实现时确定。
- 前端在请求处理中禁止重复提交，允许用户取消等待。

## 10. 接口草案

### `POST /api/convert`

请求字段：

```json
{
  "text": "原始内容",
  "inputType": "markdown",
  "sourceLocale": "zh-CN",
  "targetLocale": "zh-TW",
  "glossaryId": null,
  "convertPunctuation": true,
  "convertFullWidth": false
}
```

响应字段：

```json
{
  "jobId": "job_xxx",
  "status": "succeeded",
  "output": "转换结果",
  "inputChars": 1000,
  "outputChars": 1000,
  "appliedTermCount": 4,
  "durationMs": 38
}
```

### 其他接口

- `GET /api/conversions`：查询历史记录
- `GET /api/conversions/:id`：查看任务
- `DELETE /api/conversions/:id`：删除任务
- `GET /api/glossaries`：查询词汇表
- `POST /api/glossaries`：创建词汇表
- `PATCH /api/glossaries/:id`：修改词汇表
- `POST /api/glossaries/:id/terms`：添加词条
- `DELETE /api/glossaries/:id/terms/:termId`：删除词条

## 11. 额度与访问规则

MVP 先使用额度模型，不接支付：

| 用户类型 | 单次上限 | 周期额度 | 历史记录 |
| --- | ---: | ---: | --- |
| 游客 | 10,000 字符 | 30,000 字符 / 天 | 不保存或仅保存当前会话 |
| 注册用户 | 100,000 字符 | 1,000,000 字符 / 月 | 保存 30 天 |
| 内部测试账号 | 可配置 | 可配置 | 保存 90 天 |

这些数值是初始建议值，需要根据真实使用成本调整。

必须实现：

- IP、匿名会话和用户维度的基础限流。
- 服务端重新计算字符数，不能信任前端传值。
- 超额时返回明确错误码和升级提示。
- 不在日志中记录完整原文。

## 12. 隐私与安全要求

- 全站使用 HTTPS。
- 用户只能读取自己的历史记录和词汇表。
- 数据库查询必须带用户范围条件。
- 日志默认记录任务 ID，不记录完整文本。
- 删除历史记录时同时删除对应的输入和输出内容。
- 第三方转换服务不是默认依赖，避免将用户原文发送到不必要的外部服务。
- 产品页面明确说明：转换结果不是人工校对结果。

## 13. 埋点与产品指标

### 关键事件

- `conversion_started`
- `conversion_succeeded`
- `conversion_failed`
- `result_copied`
- `result_downloaded`
- `glossary_created`
- `glossary_term_applied`
- `signup_completed`

### MVP 判断标准

首批用户试用后重点观察：

- 首次转换完成率达到 70% 以上。
- 完成转换的用户中，复制或下载比例达到 50% 以上。
- 注册用户 7 日内再次转换比例达到 25% 以上。
- 失败任务占比低于 2%。
- 至少有一部分用户主动创建或使用词汇表。

这些不是最终商业目标，而是判断核心流程是否成立的初始指标。

## 14. 开发里程碑

### M0：产品骨架

- 初始化项目和页面布局。
- 建立转换请求和错误状态模型。
- 完成纯文本转换。

### M1：核心转换工作台

- 双栏编辑器。
- 方向和地区选择。
- OpenCC 转换。
- 复制、下载和字符统计。
- 游客额度限制。

### M2：格式与词汇表

- Markdown 和基础 HTML 保护。
- 自定义词汇表。
- 转换差异统计。
- 失败重试和结构校验。

### M3：SaaS 基础能力

- 注册登录。
- 历史记录。
- 用户额度。
- 数据删除。
- 基础埋点和管理查询。

### M4：内测验收

- 准备 30 组覆盖不同地区词汇的测试样本。
- 邀请 5 到 10 名目标用户试用。
- 收集人工修正内容和失败样本。
- 根据真实样本补充默认词表和产品提示。

## 15. 验收标准

### 功能验收

- 用户无需登录即可完成小文本转换。
- 简体、通用繁体、台湾正体、香港繁体的主要路径可用。
- Markdown 标题、列表、链接、代码块不被破坏。
- HTML 标签和 URL 不被转换。
- 自定义词条覆盖默认结果。
- 复制和下载结果与预览一致。
- 转换失败时原文仍然可恢复。
- 游客和注册用户额度生效。
- 用户只能访问自己的历史记录和词汇表。

### 质量验收

- 30 组固定样本转换结果可重复。
- 任务失败率、平均耗时和字符量可以查询。
- 前端不会因大文本输入卡死。
- 移动端可以完成输入、转换和复制。
- 删除历史记录后，输入和输出内容不再可读取。

## 16. 待决策项

以下问题在开始 M1 前确定即可：

1. 第一批用户是否以台湾内容发布者为主，还是同时覆盖香港用户。
2. 是否默认保存用户原文，还是只保存注册用户主动保存的任务。
3. 地区词汇转换是否使用 OpenCC 默认配置，还是在首批样本基础上维护产品词表。
4. 是否在 MVP 阶段支持文件上传，还是先只支持粘贴文本。
5. 部署平台和认证服务是否使用现有团队基础设施。

## 17. 推荐的第一步

先完成一个不带登录的可用闭环：

```text
纯文本输入
  -> 选择简繁方向
  -> 转换
  -> 复制结果
```

然后用真实文章验证三件事：转换结果是否可信、格式是否能保留、用户是否愿意重复使用。只有这三个问题得到正向反馈，再投入历史记录、词汇表和收费体系。
